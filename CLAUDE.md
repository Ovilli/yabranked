# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```sh
./gradlew test                                  # all unit + API tests
./gradlew :proto:test :backend:test :client:test  # what CI runs (agent needs mavenLocal, see below)
./gradlew :agent-core:test                      # the agent's testable half (CI runs this)
./gradlew :backend:test                         # one module
./gradlew :backend:test --tests '*MatchServiceTest*'          # one class
./gradlew :backend:test --tests '*MatchServiceTest.settle*'   # one test
./gradlew :backend:run --args="--fake-auth"     # backend on :8080, no Mojang verify
./gradlew :backend:runMock                      # 2 fake players queue + match (needs a --fake-auth backend)
./gradlew :client:runClient                     # dev client, username AliceDev, runDir client/run
./gradlew :client:runClient2                    # second instance, BobDev, runDir client/run2
./gradlew :agent:build :backend:installDist     # artifacts for the Docker match-server flow
```

Match-server image (needs the YAB repo checked out at `../bingo`, override with `$YAB_REPO`):

```sh
(cd ../bingo && ./gradlew :api:publishToMavenLocal :mc26.2:build)
./gradlew :agent:build && docker/fetch-mods.sh && docker build -t yabranked-match docker/
```

`agent` depends on `me.jfenn.bingo:api` from **mavenLocal**, and `settings.gradle.kts` leaves the module out of the build entirely until the YAB repo has published it — see [CI](#ci) for why that has to happen in `settings.gradle.kts` rather than by not asking for its tasks.

### Toolchains

`proto` and `backend` target JVM 21; `agent` and `client` target JVM 25 (MC 26.2 requires it), so the **Gradle JVM itself must be Java 25**. That requirement lives in `gradle/gradle-daemon-jvm.properties` (`toolchainVersion=25` plus a per-platform download URL), which Gradle reads *before* it starts the daemon and auto-provisions from — so any launcher JVM works and nothing has to be installed first. Regenerate it with `./gradlew updateDaemonJvm --jvm-version=25`.

It used to be `org.gradle.java.home` in `gradle.properties` pointing at an absolute path under `/home/ovilli/.gradle/jdks/…`, which meant the build only worked on that one machine and had to be edited out by hand everywhere else — CI included, which is part of why there was none.

### CI

`.github/workflows/ci.yml` runs `:proto:test :backend:test` in one job and `:client:test` (Loom, so a Minecraft download) in another, plus a syntax gate on `deploy/admin/app.py`.

`:agent-core` carries the agent's testable logic precisely so CI has something of the agent to run; `:agent` itself never builds here.

**`agent` is included by `settings.gradle.kts` only when `me.jfenn.bingo:api` is really in mavenLocal**, and that condition is not a convenience. Loom resolves that dependency at *configuration* time, and Gradle configures every project in a build whatever task was asked for — so on a machine without a YAB checkout the missing artifact failed `./gradlew :backend:test` and `./gradlew projects` too, with an error naming a module the caller never mentioned. Excluding it from the task list does nothing. The repo was unbuildable for anyone who had not published YAB first, which CI found by being the first such machine. `-PskipAgent=true` reproduces the trimmed build where the artifact *is* present; the cost of all this is that `./gradlew projects` is not the same everywhere.

The runner having Docker is load-bearing — `PostgresStoreTest` `assumeTrue`-skips silently without it, so CI is the only place the SQL stores are exercised at all. A step after the tests reads the JUnit XML and raises a workflow warning if that class skipped, because a silent skip is indistinguishable from a pass.

## Architecture

Five Gradle modules, one shared wire model:

- **`proto`** — every DTO on every wire (HTTP + queue/party WebSockets + agent reports). Plain library, no Minecraft deps. Split only for size: `Model.kt` (session, profile, match, queue) and `Social.kt` (friends, parties, endorsements, leaderboard categories); the same rules apply to both.
- **`backend`** — Ktor/Netty service: auth, matchmaking, rating, match records, orchestration.
- **`agent-core`** — the agent's Minecraft-free half: `AgentConfig` (env parsing), `VoidDeadlines` (the pre-game void rules), `ReplayFormat`/`ReplayStream` (the `.yabr` writer), `AgentJson`. Depends on `:proto`, and **the agent no longer mirrors any proto type**: `MatchRules`, `MatchResultReport`, `MatchOutcome`, `MatchReplayMeta` and the `Replay*` types are the *same classes* the backend encodes and decodes with — the agent used to carry a hand-copied one under a comment claiming proto could not be nested into a mod jar, which stopped being true when `:client` solved it by flattening. Plain library, no Loom, **no YAB dependency — which is the entire point**: `:agent` cannot be built in CI, so anything testable that stays in it is untested forever. This module is always in the build and always tested. Put new agent logic here by default; only code that genuinely needs a `MinecraftServer` belongs in `:agent`.
- **`agent`** — server-side Fabric mod that runs *inside* an ephemeral match container and drives one YAB game. What is left here is the Minecraft coupling itself: the Netty tap, the mixin accessors, the YAB driving. **It has no test source set on purpose** — a suite here would never run anywhere. `agent-core`'s classes **and `:proto`'s** are **flattened into the mod jar** by the `bundledCore` configuration, the same trick `:client` uses for `:proto` and for the same reason (Fabric JiJ only loads nested jars that are themselves mods). That configuration is non-transitive — kotlinx-serialization and slf4j come from the game and must not be dragged in — so **every project whose classes are needed must be listed on it by hand**; `:proto` is easy to forget there because `:agent-core` already compiles without it. Getting that wrong is not a loud failure: the mod would load and then `NoClassDefFoundError` inside `AgentConfig.fromEnv`, which is indistinguishable from an agent correctly deciding to stay inert.
- **`client`** — client-side Fabric mod: title-screen "Ranked" button and all ranked UI.

### Match lifecycle (the path worth knowing)

1. Client `POST /v1/auth/session` with a Mojang `joinServer` serverId → backend `hasJoined` check (`auth/MojangSessionVerifier.kt`) → bearer token in the in-memory `TokenRegistry` (`api/Api.kt`).
2. Client opens `WS /v1/queue?token=…` and sends `JoinQueue`. `QueueService` ticks `MatchmakingQueue` once a second under a `Mutex`. The queue's unit is a **`QueueTicket`** — a lone player, or a party that matches together and is never split across sides — rated by the ticket's *median* MMR. Each ticket's band widens by `bandPerSecond` the longer it waits; a tick assembles exactly `MatchFormat.playerCount` players out of tickets the seeker accepts, then `formSides` either plays the tickets as-is (party vs party) or packs them emptiest-and-weakest-first (the XvX snake draft). `tick()` returns `QueuePairing`s; a two-player one converts to the legacy `QueueMatch`.
3. `MatchService.createMatch` writes a `PENDING` `MatchRecord` with a per-match `serverToken`, world seed and card seed, then fires `onMatchCreated`.
4. `MatchOrchestrator` (only when `YABRANKED_ORCHESTRATE=1`) `docker run`s one `yabranked-match` container per match, passing everything as `YABRANKED_*` env (`orchestrator/ContainerRuntime.kt`). Without it, `Main.kt` registers a stub listener that marks matches ready at `pending.invalid:25565` so the queue flow stays testable.
5. Inside the container, `AgentConfig.fromEnv` reads that env — **missing any required variable makes the agent inert**, which is what keeps the mod harmless on a normal server. The agent configures YAB, gates joins to the two matched UUIDs, starts the game, then `POST /v1/internal/matches/ready`.
6. The WebSocket handler polls the match record until it is `ACTIVE` with a `serverAddress`, then pushes `MatchFound`; the client auto-connects.
7. The agent reports the outcome to `POST /v1/internal/matches/result`, authenticated by the per-match `serverToken`. `MatchService.settle` applies Elo, updates stats, evaluates achievements, and fires `onMatchSettled` — which is also what tears the container down.

### Social systems

`backend/social/` is server-authoritative and deliberately keeps its rules in the services, not the routes (`api/SocialApi.kt` only authenticates, parses ids, and maps results to status codes):

- **`FriendService`** — three rules: the target must have a player row (i.e. has used the mod at least once — *not* "has played a match with you"), their `allowFriendRequests` toggle refuses outright, and one pending request per pair. Requesting someone who already requested you auto-accepts. `POST /v1/friends/requests` takes a uuid or a name, resolved via `PlayerStore.findByName`; `GET /v1/friends/recent` is a convenience shortlist, not an allow-list.
- **`PartyService`** — one `ReentrantLock` over the whole registry; listener callbacks always fire *outside* it. A **party of one is treated as no party**: it is what every player lands in the moment they press "create", so both `invite` and `acceptInvite` let a solo member be invited away (accepting dissolves their empty lobby). Treating it as a real party made two players who had each opened the party screen permanently unable to invite each other. Clients get full `PartyView` pushes, never deltas. **The leader leaving disbands the party**; a member leaving that breaks the format's size fires `onQueueCancelled`, which `rankedApi` turns into `QueueServerMessage.QueueCancelled` for every waiting socket. `sanitize()` forces `PartyOptions.ranked` off for any shape that cannot be rated fairly (manual teams, split worlds/seeds, wrong size, unrated format).
- **`EndorsementService`** — teammates only, decided matches only, once per teammate per match, inside a 24h window.
- **`Presence`** — process-local with a 90s TTL; never persisted.

`WS /v1/party` is the party control channel and also how invites and friend requests reach an online player. Only the leader's queue socket holds the party's ticket; every other member's client opens a socket too (as an *observer*) purely so the backend can tell them where the match server is.

### Moderation

`moderation/ModerationService.kt` owns both halves of a report: who the accused is, and what a moderator decided.

**A report has a lifecycle, and the reason is retention rather than tidiness.** `ReportStatus` is `OPEN | REVIEWING | ACTIONED | DISMISSED`, and `ReportStatus.open` (the first two) is what pins the match recording. Filing sets `replays.under_review`; before `POST /v1/admin/reports/{id}/resolve` existed nothing could ever clear it, so every reported match's packet capture — tens of megabytes a player — was kept forever on a Pi with a nearly full SD card. Nothing recorded that a moderator had looked, either, so the same account could be reported indefinitely with no way to see it had already been judged.

- **The hold is released per match, not per report.** Two players reporting the same opponent produce two rows and the recording is the evidence for both, so `resolve` re-reads `forMatch` and only clears `under_review` when nothing there is still open. `ReplayApi.ensureRow` asks the same question (`any { it.status.open }`) rather than "are there any reports", or a row created after a decision would silently pin it again.
- **`REVIEWING` is a claim, not a decision**: it holds the recording and writes no `resolvedAt`. A later transition that names no moderator or note keeps what an earlier one recorded (`COALESCE` in SQL, `?:` in memory).
- **`GET /v1/admin/reports` takes `?status=`, and an unknown one is a 400.** Unfiltered, the queue mixes fresh accusations in with everything already judged, which is how it reads as endless. Each row carries `reportsAgainst` — every report ever filed against that account — because the list is ordered by recency, which surfaces whoever was reported *last* rather than whoever is reported constantly.
- **Migration V6 replaced `UNIQUE (match_id, reporter)` with `(match_id, reporter, accused)`.** The application rule became one report per *accused* per match when team formats landed and `ReportStore` was changed to match; the baseline constraint was not, so reporting a second opponent in a 4v4 passed the check and then died on the insert. Only Postgres was affected — every test ran against the in-memory store, which has no constraints. It is the standing example of why `PostgresStoreTest` skipping silently is a problem.
- Admin wire types (`ResolveReportRequest`, `AdminReportJson`) are declared in `api/Api.kt`, **not** `:proto`: the player client never sees an admin route, and putting them in the shared module would ship the moderation vocabulary in every mod jar and make it a compatibility surface. The only consumer is `deploy/admin/`, whose Reports tab calls the backend over loopback with `YABRANKED_ADMIN_TOKEN`.

### Rating and stats, per mode

Two ladders, deliberately separate:

- `season_stats` keeps its exact original meaning — the **solo 1v1 ranked ladder**, moved only by one-a-side rated matches via `EloRatingSystem`.
- `mode_stats` (keyed `(uuid, season, format)`) is written for **every participant of every decided match, casual included** — that is what makes the profile's per-mode playtime breakdown and the per-mode leaderboards possible. Team formats are rated on it by `EloTeamRatingSystem`, which scores a *side's mean* rating so carrying a weaker teammate is worth more than beating an equal opponent alone.

`MatchRecord.rated` (persisted, defaults true) is what decides whether a settle moves anything: a party may play a rated format unrated, and that decision has to survive a restart.

`MatchRecord.teams` empty means a legacy 1v1 described by `playerA`/`playerB`; `rosters`/`participants`/`sideOf`/`didWin` synthesise the two-side view so every pre-team query and test still works. In Postgres the flattened `matches.participants uuid[]` (GIN indexed) is what "matches this player was in" searches — `player_a`/`player_b` are only each side's first player once teams exist.

Both internal endpoints authenticate with the match's `serverToken` compared via `MessageDigest.isEqual`; the orchestrator is the only component that ever sees it.

**The match image is Alpine-based, and that is not a size preference.** On a 16 KB-page aarch64 host — a Raspberry Pi 5 is the one this was found on — the glibc Temurin images cannot run a JVM at all: `java -XshowSettings:properties -version` dies with a bare `Exception in thread "main"`, and the Fabric launcher reports `A JNI error has occurred`, which reads like a corrupt jar and is not. The same JVM version on musl works, and so does the host's own JVM, so it is the image's glibc rather than the JVM, the kernel or the hardware. Match servers have no choice but to run in a container, so the base has to be one that works on hosts people actually own. `entrypoint.sh` is `#!/bin/sh` with no GNU-isms, so nothing else changes.

**Container runtimes older than the kernel corrupt images silently.** Docker 26.1.5 with runc 1.1.15 on kernel 6.18 produced image layers with damaged files — a `postgresql-42.7.7.jar` that came out as sha `de5196c7…` against the canonical `157963d6…`. The symptoms never mention corruption: Gradle failed with `Index -469035871 out of bounds for length 6488`, the JVM SIGSEGV'd reading its own `lib/modules`, and MinIO segfaulted on restart. Upgrading to Docker 29.6.2 / containerd 2.2.6 / runc 1.3.6 fixed the cause, but **anything built or pulled beforehand stays broken**, including BuildKit's cache — a rebuild silently reuses the poisoned layers unless it is `--no-cache --pull`.

**`max-tick-time=-1` in `docker/entrypoint.sh` is load-bearing.** YAB pre-generates the teams' spawn areas and reads blocks from the main thread while doing it, so `getBlockState` blocks on chunk generation *inside a single tick* by design. On a CPU-limited container that tick can take minutes — an observed match spent 2m2s preloading 162 chunks and was then killed by the vanilla watchdog's 60s default, mid-setup, losing the match for both players. The server was slow, not hung.

**A container that dies after going ACTIVE is swept by `MatchOrchestrator.sweepDeadContainers`** (every `livenessInterval`, default 30s, via `ContainerRuntime.isRunning`). The ready-timeout reaper only looks at `PENDING`, so before this a crashed match server left the row ACTIVE forever, its port never released, and both players holding a match they could neither finish nor leave. The sweep voids — nobody finished, so no rating should move. `isRunning` answers `true` when the runtime itself is unreachable: "docker is briefly down" must never be read as "every live match has died".

**The client's "I am in a match" flag is reconciled against the backend, not just against the connection.** `RankedState.activeMatch` used to be cleared only by `ClientPlayConnectionEvents.DISCONNECT`, so a match that ended while the player sat in the menus — a teammate conceding, an orchestrator reaping a server that never came up — left the client wedged: no queue button, no result screen, and nothing on offer but "Forfeit" for a match already decided. `GET /v1/players/me/match` (`MatchStore.liveFor`, GIN-indexed on `participants`) answers "am I still in one", polled from the client tick every 5s **only** while in the menus with a match on the books. A failed or offline fetch is deliberately not an answer — reading a flaky request as "your match is over" would cancel a match the player is about to be sent into. `YabRankedClient.matchEnded` is the single wind-down path shared by all three triggers (disconnect, reconcile, conceding from the menus), and it claims the result-loading screen off `MatchResultLoadingScreen.removed()` rather than a fixed tick budget, because a slow container teardown used to outlast the old five-tick window and leave the player on vanilla's "Disconnected".

**Conceding has two channels, and both are needed.** The agent registers a `/forfeit` command inside the container, and a disconnect mid-match forfeits on the spot — there is no reconnect grace period, because a player who leaves a ranked match cannot rejoin it, so the countdown only ever made the winner wait for something that could not happen. Neither is reachable from a client that is not connected to the match server — a crash, an alt-F4, or simply backing out to the ranked menu — so `POST /v1/matches/{id}/forfeit` settles the same match over the player's own bearer token. `MatchService.forfeit` is authorised by *participation*, not by the `serverToken`: the only thing it can express is "my side loses", so there is nothing there to abuse. Whichever channel lands first settles; the second gets `AlreadySettled` and is discarded.

### Storage

`store/Stores.kt` defines `PlayerStore` / `MatchStore` / `ReportStore` / `AchievementStore` plus in-memory implementations; `store/PostgresStores.kt` implements the same interfaces. `Main.kt` picks Postgres only when `YABRANKED_DATABASE_URL` is set, otherwise in-memory (state lost on restart).

Consequences to keep in mind:
- **Every test except `store/PostgresStoreTest.kt` runs against the in-memory stores**, so SQL paths are barely covered. `PostgresStoreTest` spins up `postgres:16-alpine` via `docker run` and `assumeTrue`-skips silently when Docker is absent.
- Schema changes are **versioned migrations**, not appends to the baseline. `schema.sql` is migration 1 and is never edited again; every later change is a new file under `resources/migrations/` plus an entry in `SchemaMigrator.ALL` (`store/Migrations.kt`). A database that has the tables but no `schema_version` row is *baselined* rather than re-migrated.
- Ratings are season-scoped (`season_stats` keyed `(uuid, season)`); `SeasonService` holds the current season number and persists it through `PostgresSettingsStore`. It only advances via `POST /v1/admin/seasons/advance`.
- `store/SocialStores.kt` adds `FriendStore` / `EndorsementStore` / `ModeStatsStore` with in-memory implementations; `store/PostgresSocialStores.kt` implements the same interfaces. Rosters, per-side seeds and the privacy block are stored as JSON text via `SocialJson` — they are small, always read whole, and never queried into, so a column per field would mean a migration per toggle.
- `store/ReplayStores.kt` adds `ReplayStore` (+ `PostgresReplayStore`) for replay *metadata*; the packet bytes are in `store/ReplayBlobStores.kt` and never in the database. See **Replays** below.

### Replays

Every match records one, and a recording is **a packet capture, not a description**: the agent taps every clientbound packet the match server sends each participant and stores the bytes verbatim, and the client feeds them back into a detached `Connection` so the viewer stands in the real world — the terrain as it generated, the chests as they were looted, the other players walking through it. The format before this sampled positions once a second and drew them as a chart, which could show a route and could never show a match. It exists for two audiences: a player watching their own game back, and a moderator deciding whether "he was cheating" holds up, which is now a question the recording can actually answer.

**Where the bytes are taken from is the whole design.** `agent/ReplayPacketTap.kt` inserts a Netty handler **immediately head-ward of the `encoder`**, which on a server pipeline puts it between `encoder` and `compress` (verified against 26.2: `configureSerialization` adds `prepender` then the encoder, `setupCompression` adds `compress` *after* `prepender`, `setEncryptionKey` adds `encrypt` before it). Outbound data travels tail→head, so the tap sees packets that are already bundle-split and encoded and not yet compressed or encrypted — the one position where the bytes are self-contained *and* independent of `network-compression-threshold` and `online-mode`. The protocol is read per frame from whatever sits under the `encoder` name (`PacketEncoderAccessor`), never inferred from a phase guess: the phase boundary is exactly where a guess goes wrong, and a mislabelled frame is a malformed packet in the middle of an already-drawn world.

- **Capture starts at `ServerConfigurationConnectionEvents.BEFORE_CONFIGURE`, not at the match.** The configuration phase carries the dynamic registries, and a stream without them is not a shorter replay, it is an undecodable one. Login and handshake frames are dropped — they describe how *that* client authenticated, and the viewer starts its fake connection in the configuration phase with a profile it makes up. The consequence is that the recording's t=0 is earlier than the match: `MatchReplayMeta.recordedFrom` anchors it and `gameStartMillis` is where the playhead opens.
- **Four mixin accessors in `agent/src/main/java/.../mixin/`** (`yabranked-agent.mixins.json`) exist only to reach protected/private fields the tap needs: `ServerCommonPacketListenerImpl.connection`, `Connection.channel`, `PacketEncoder.protocolInfo`, and `ServerConfigurationPacketListenerImpl.gameProfile`. **The last one is not optional and `Connection.getIntendedProfileId()` is not a substitute**: that field is only set by `ServerConnectionListener.acceptChannel(Channel, UUID)` — the memory and transfer path — and never by the initializer `startTcpServerListener` installs, so on a match server it is always null. The first live run recorded nothing at all for exactly this reason, and said nothing about it, which is why every early return in `ReplayPacketTap.attach` now logs and why `ReplayRecorder.checkpoint` warns when there is nothing to upload.
- **Streams are per participant and merge cleanly.** Entity ids and chunk coordinates are the server's, so feeding a second stream into one world widens it rather than corrupting it. But a stream only contains what its recipient was sent, so watching is always watching from inside one player's field of view — which is why the viewer *asks* whose, and why switching is a re-open.
- **Frames are written to disk in the container as they are captured** (`<tmp>/yabranked-replay/<matchId>/stream-N.yabr`), layout `"YABR" | u8 version=2` then `u8 protocol | u32 millisSinceStart | u32 length | payload`. **The writer (`agent/ReplayPacketTap.kt`) and the reader (`client/replay/ReplayStreamFile.kt`) share no code** — `MAGIC`, `FORMAT_VERSION`, the 5-byte file header and the 9-byte frame header are each declared twice, once per module, and nothing fails at build time when they drift. What happens instead is that the reader returns null for every stream and the player is told the match has no recording. Both sides therefore have a test that pins the bytes as *literals* rather than against its own constants (`ReplayStreamTest`, `ReplayStreamFileTest.the reader accepts exactly the bytes the agent writes`); only the reader's half runs in CI. Holding a match in memory is not an option at tens of megabytes a player, on the machine playing the match. Per-stream cap `ReplayPacketTap.DEFAULT_MAX_BYTES` (96 MB); past it the stream closes and is reported `truncated`, which the client shows rather than hides.
- **The upload is incremental and offset-addressed, and runs *during* the match.** `ReplayUploader` ships stream tails to `POST /v1/internal/matches/{id}/replay/streams/{index}?offset=N` (octet-stream) and the backend answers with the length it holds — `200` when the chunk extended the stream, `409` with the same `{"length":N}` when the offset was stale. That answer is what makes a retry safe: a dying container cannot know whether its timed-out request applied, and with this it does not need to. `ReplayApi` decides which by reading the length *before* appending; the after-value cannot distinguish "applied" from "ignored".
- **The index goes up separately and last**, to `POST /v1/internal/matches/{id}/replay?complete=true|false` — `MatchReplayMeta`, the card and the timeline, still polled from the bingo API because it exposes the board and `hasPlayerAchieved` and no claim event. `complete=false` is a checkpoint (`YABRANKED_REPLAY_CHECKPOINT_SECONDS`, default 60s, 0 disables) and publishes a partial recording, which is playable up to where the upload got to. Both agent-facing routes still authenticate with the per-match `serverToken`.
- **The index still lands *before* the result report**, and that order is as load-bearing as it was: settling fires `onMatchSettled`, which is `docker rm -f` on the container doing the uploading. Its timeout is capped at 8s so it cannot push the result past the client's poll window. What changed is that losing that race now costs the last few seconds rather than the whole match, because the packets went up while the game was being played.
- **The packets are not in Postgres.** `store/ReplayBlobStores.kt` holds them — `FileReplayBlobStore` under `YABRANKED_REPLAY_DIR`, `InMemoryReplayBlobStore` when none is set (lost on restart, the same bargain the in-memory stores make). The `replays` row keeps only `meta`, `size_bytes` and `complete`; migration V5 drops `payload` and **deletes every existing row**, because a v1 payload has no packets in it to salvage. `ReplayStore.pruneExpired` therefore returns the ids it dropped, so `ReplaySweep` can delete the bytes — rows first, bytes second, since the other order briefly hands a player an empty world.
- **A settled match's container is not reaped for `OrchestratorConfig.settleGrace`** (`postgameSeconds` + 15s), and only when the outcome is not `VOID`. `onMatchSettled` used to `docker rm -f` the instant the result row was written, which SIGKILLed a container that was still working. Voided matches are still torn down at once; there is nothing to read and nothing to upload, and a never-ready container must not sit on its port.
- **There is no postgame linger.** Players are disconnected as soon as the result is reported (`YabRankedAgent.endSessionAndShutdown`, capped at `MAX_WIND_DOWN_SECONDS` = 3s whatever `YABRANKED_POSTGAME_SECONDS` says). The linger used to be 20s so players could read YAB's game-over screen, and it was a hazard dressed as a courtesy: YAB's POSTGAME ends the instant a surviving player presses ready — "return to lobby" — and ending it resets the worlds and drops everyone into a fresh bingo lobby game on a new team. No window short enough to be safe is long enough to be useful, because the button exists for as long as the window does. It was also *why the result screen was late*: `YabRankedClient.matchEnded` hangs off `DISCONNECT`, so every lingering second was a second the player waited for the ranked result that is the point of a ranked match. The recording is unaffected — `replay.flush` is synchronous and completes before the result report. The agent still ignores `GAME_STARTED` once the match is `REPORTED`, and players are still disconnected with a reason rather than dropped when the process halts.
- **The no-show timeout is 90s, not 300s, and it narrates itself.** It is time a player who *did* connect spends alone in a bingo lobby, which at five minutes reads as a broken match server rather than as a wait — and the usual cause is a client that died the instant it was matched, which will not arrive however long the timer is. (The queue socket's `finally` deliberately does not dequeue an already-matched player, so a client dying at that moment always produces this.) The agent announces the wait at 15s and 45s — **only while somebody is actually missing** — and says "your opponent never connected" when it voids.
- **Arrival and "the game started" are separate deadlines, and conflating them voided live matches.** The no-show rule is decided by `arrived`, a set filled by `ServerPlayConnectionEvents.JOIN`; it used to be inferred from the phase, which only leaves `WAITING_FOR_PLAYERS` when *YAB* reaches `GameState.PLAYING`. On a CPU-limited container those are a minute or more apart — YAB's `findSpawnPosAsync` runs to a 60s timeout of its own and the chunk preload after it takes tens of seconds — so an observed match with both players on their teams for 80 seconds was voided six seconds before its countdown ended, telling both of them their opponent had never connected. Everyone-present-but-not-started now has its own, longer deadline (`noShowTimeoutSeconds + START_GRACE_SECONDS`, i.e. 90s + 180s) that voids with a different message, because a game stuck in `STARTING` still has to end: the orchestrator's ready-timeout reaper only looks at `PENDING`. A player who disconnects before the start is removed from `arrived`, so the no-show rule applies to them again rather than counting them present forever.
- **`YABRANKED_MATCH_CPUS` is a correctness setting, not a throughput one.** At two cores YAB's spawn search times out and falls back to a worse position; four is the default for that reason, and a deployment that lowers it is buying a minute of dead time at the start of every match.
- **Retention still has three independent reasons** and none may override another: `expires_at` (`ReplayPolicy.retentionDays`), `replay_saves` (players who pinned it, capped by `savedPerPlayer` **and now `savedBytesPerPlayer`** — ten packet captures are a hundred times the ten sample tracks the file count was chosen for), and `under_review` (the hold `POST /v1/reports` puts on a reported match).
- **Who may watch**: participants (`MatchRecord.sideOf`) and admins, for the index *and* every stream range. A capture is everything the recipients' clients were told, so handing one out is handing out a scouting report of a base the recipient has never seen. Both refusals answer 404 for the same reason the forfeit route does.

**Client playback** lives in `client/.../replay/`:

- `ReplayCache` downloads first and watches second, resumably, because playback feeds packets at the wall-clock rate they were captured and cannot stop for the network mid-match. `ReplayStreamFile` indexes a stream in one scan and **stops at the last whole frame** — a half-written frame is the ordinary shape of a checkpointed upload, not an error.
- `ReplayPlayback` builds a `Connection(PacketFlow.CLIENTBOUND)` over an `EmbeddedChannel`, configures it exactly as a real client connection, and hands it a `ClientConfigurationPacketListenerImpl` with a fabricated `CommonListenerCookie`. Frames are written inbound **length-prefixed**, because the pipeline's head is the frame splitter. Vanilla does the rest: `handleConfigurationFinished` swaps to `GameProtocols.CLIENTBOUND` and builds the `ClientPacketListener`, the `ClientLevel` and the `LocalPlayer` itself. **Every serverbound reply is swallowed by an `OutboundSink` added tail-most**, and that is not an optimisation: on a *client* pipeline `configureSerialization` installs a real `PacketEncoder(INITIAL_PROTOCOL)` at `"encoder"`, so the client's first reply — Fabric's attachment sync answering a configuration custom payload — hits `Sending unknown packet 'serverbound/minecraft:custom_payload'`, and an `EncoderException` is a connection *fault*: `Connection.exceptionCaught` disconnects and the next frame dies with `ClosedChannelException`. `setupOutboundProtocol` does **not** fix this and was tried — it writes an `OutboundConfigurationTask`, and the only handler that runs one is `UnconfiguredPipelineHandler$Outbound`, which is installed on the server side only. The sink drops `Packet`s and passes everything else, because the inbound protocol swap travels as a non-packet outbound message. `channel.pipeline().fireChannelActive()` is required — Netty does not replay `channelActive` for handlers added after registration, so the `Connection` would never learn its own channel.
- **It is driven from the client tick, on the render thread.** `PacketUtils.ensureRunningOnSameThread` then applies each packet inline instead of deferring it. Outside a seek no more than `MAX_FRAMES_PER_TICK` are applied per tick, so a chunk-heavy second is not paid for in one frame.
- **Seeking backwards is a restart-and-fast-forward.** A packet stream is deltas; there is no packet that puts a block back.
- The camera is free without any interception, because a player's own movement is never sent back to them — so nothing in the stream fights the viewer for it. Spectator is re-asserted every tick (`MultiPlayerGameMode.setLocalMode`) since the recording sets the game mode the player actually had.
- **The players' bodies do not come from the packets, and cannot.** Movement is client-authoritative, so a server never sends a player their own position: player N is the one player absent from stream N, and an opponent only exists in it while inside tracking range. `MatchReplayMeta.tracks` therefore carries a 5 Hz position sample per player (`ReplayTrack.SAMPLE_HZ`, sampled on the server thread by `ReplayRecorder`), and `ReplayGhosts` drives a `RemotePlayer` along it. **A body stands down the moment the real entity is present** — that entity is the recording and the track is only an interpolation of it — but never for the viewer themselves, who is an invisible spectator and would otherwise be the one player with no body. Bodies carry a *derived* uuid (`GHOST_SALT`), not the player's, because a level indexes players by uuid and the viewer already holds the real one — and `ReplayBody` overrides `getSkin()` to look the skin up with the **real** id, since the derived one matches nobody and would render a default Steve wearing the right name. No mixin: `AbstractClientPlayer.getSkin` is public and non-final, and a subclass is narrower than rewriting a method every player entity in the game runs. The textures are already on the client because a recording carries the server's whole player list, the recipient's own entry included. Recordings made before this have no tracks, and the HUD says so rather than leaving the follow key looking broken.
- `ReplayHud` draws the timeline in-world (a tick per marked moment); **the controls are buttons on `ReplayControlsScreen`, not key mappings**. They were nine bindings, on the reasoning that an in-world overlay cannot take a click — true, and the wrong conclusion: the answer is a screen you can open, not a control surface nobody can find. One key opens it (the ranked key, reused while watching) and everything else — play/pause, ±10s, speed, moment-to-moment, follow, teleport, stop — is a button, plus a scrub bar that seeks where you click it. The panel sets `isPauseScreen() = false` and draws no scrim, so the recording keeps playing behind the controls that are acting on it. **Following is held by player *name*, not by entity**: a backwards seek destroys and rebuilds the world, and a camera left riding a dead entity is a black screen. Playback stops at the last frame rather than looping or exiting: the end is often the interesting part, and exiting on its own would throw the viewer out of a world they may still want to fly around.

### Rating

`rating/RatingSystem.kt` is the interface; `EloRatingSystem` is the only implementation (initial 1000, K=80 during the 5 placement matches, K=32 after, floor 0). `rating/Tier.kt` turns a rating into the `"Gold II"` display string the client parses back apart. Note `placementMatches = 5` is declared independently in both `MatchService` and `EloRatingSystem`.

### Client ↔ proto coupling

`:proto`'s classes are **flattened into the client mod jar** by the custom `bundledProto` configuration in `client/build.gradle.kts` — Fabric JiJ only loads nested jars that are themselves mods, and proto is a plain library. Adding a proto type therefore needs no build change, but the client jar must be rebuilt for the client to see it.

Every module that (de)serializes must configure Json identically: `ignoreUnknownKeys = true` and `classDiscriminator = "type"`. That instance is re-declared per module (`api/Api.kt`, `client/BackendClient.kt`) rather than shared — change one, change all. The agent is the exception: it has one `AgentJson` in `:agent-core`, and **`encodeDefaults` staying false there is load-bearing**, not incidental. `MatchReplayMeta.format` exists on the shared type but the agent must not fill it in — the backend knows the format from the match row it is already reading, and `ReplayApi` stores the uploaded index **verbatim**, so a guessed value would be persisted and served back. Defaults being omitted is the only thing keeping that field off the wire; `AgentWireFormatTest` asserts it rather than trusting it.

Backward compatibility rests entirely on `ignoreUnknownKeys` plus default values on new fields, and on the `clientVersion` gate: setting `YABRANKED_MIN_CLIENT_VERSION` makes `/v1/auth/session` answer 426 to older clients.

`MatchFormat` is no longer one of those hazards: it has a custom `MatchFormatSerializer` keyed on its `wire` name that decodes anything unknown to `MatchFormat.UNSUPPORTED`, so adding a mode is safe. **Adding a `QueueServerMessage` or `PartyServerMessage` subtype is still a breaking change for existing clients** — an unknown `type` discriminator fails to decode.

All `BackendClient` methods block. Call them from `YabRankedClient.workers` (a single-thread executor) and hop back with `minecraft.execute { … }`; never from the render thread.

### Client UI invariants

- **Every ranked screen extends `ui/ScaledScreen.kt`, and lays out in *virtual* pixels.** A vanilla screen is laid out in GUI-scaled pixels, so raising the GUI scale shrinks the space it has: at scale 4 on 1080p that is 480×270, and the ranked menu alone needs ~420×360, so half its buttons were drawn off the bottom and could not be clicked. `ScaledScreen` picks the largest **whole** scale no greater than the player's that still covers `DESIGN_WIDTH`×`DESIGN_HEIGHT` (`fittingScale`, unit-tested), sets `width`/`height` to that viewport, and multiplies everything it draws by `uiScale`. Whole steps are the point — a fractional factor resamples the font and every 1px border. Consequences: the vanilla `init`/`extractBackground`/`extractRenderState`/`mouse*` are **final**, and screens override `layout`/`drawBackdrop`/`drawContent`/`onMouse*` instead, which is where the transform has already been applied; `applyViewport` reads the *window*, never the inherited `width`, because `rebuildWidgets()` re-runs `init()` without resetting it and the screen would shrink a step on every refresh; and anything drawn **outside** a screen (the notice stack, the queue badge) is still in the game's coordinates and must be positioned from `window.guiScaledWidth`, not `screen.width`.
- **Ranked screens draw their own hover labels** (`RankedButton.hoverTip` → `Ui.tooltip`, drawn last by `ScaledScreen`) rather than calling `setTooltip`. Vanilla defers a widget tooltip until after the screen's render pass, which puts it outside the transform above — positioned and sized in the game's coordinates instead of the screen's. `RankedButton`/`IconButton` on a *vanilla* screen (the title and pause screens) still use `setTooltip`, since nothing there is looking at `hoverTip`.
- **A player head needs the profile fetched first.** `SkinManager.get` reads the `textures` property off the `GameProfile` it is handed and resolves to `MinecraftProfileTextures.EMPTY` when there is none — it never calls Mojang itself. `PlayerHeads` therefore does `sessionService.fetchProfile(uuid, true)` on the background executor and hands the *result* to the skin manager on the render thread; a bare `GameProfile(uuid, name)` renders every player, signed in or not, as the default Steve/Alex.
- **There is one notification stack.** `RankedNotice` owns the top-right column and `RankedToast` is now only a way into it; it used to be a vanilla `Toast` drawn by the game's own manager, so two notifications raised through different calls drew over each other. The stack is drawn from **one place** — `YabRankedClient`'s `ScreenEvents.afterExtract` hook for every screen, plus `RankedHud` in-world — never by a screen for itself, or a screen stacked on another paints it twice. The dismiss "×" is the only thing there that consumes a click.
- **`MatchHistoryEntry.rated` is not `format.ranked`.** A party may play a rated format unrated. `MatchService.settleLocked` only writes `ratingAAfter`/`ratingBAfter` when the ladder actually moved, so an unrated match reports no movement at all rather than the swing it *would* have had; every screen that draws a delta checks `rated` first.
- **A player can be reported from anywhere they are visible.** `POST /v1/reports` takes a `matchId` (post-match) *or* an `accused` uuid (from a profile), and resolves the other from the match roster — `MatchStore.between` finds the most recent shared match. The accused is always derived server-side; naming someone who was not on the other side is refused, not recorded. Those rules live in `moderation/ModerationService.kt`, not in the route.
- **Icon atlas**: `tools/gen_icons.py` appends glyphs to `icons.png`; indices are baked into `ui/Icons.kt`, so glyphs are only ever appended and `ICON_COUNT` must match the width the script prints.

## Environment variables

`config/BackendConfig.kt` parses and validates every setting once at startup — that file is the authoritative list, not `Main.kt`. Everything boolean goes through one parser that accepts `1/true/yes/on` and `0/false/no/off` and **rejects** anything else, so the old trap where `YABRANKED_ONLINE_MODE=0` *enabled* online mode is gone. A malformed value aborts startup rather than being guessed at.

- `--fake-auth` (or `YABRANKED_FAKE_AUTH=1`) both disables Mojang verification and enables `GET /v1/debug/matches/{id}/token`. Nothing stops it being combined with a real `YABRANKED_DATABASE_URL`.
- Nothing is set for `YABRANKED_MIN_CLIENT_VERSION` by default and the backend now says so at startup. An unset gate is not neutral: adding a `QueueServerMessage` or `PartyServerMessage` subtype breaks old clients on the unknown `type` discriminator, and the gate is the only thing that turns that into a 426 instead of a downstream symptom.

`YABRANKED_REPLAY_DIR` is where replay packet streams are written. Unset means they are held in memory and lost on restart — which is fine for dev and is not what a deployment wants, because a recording is tens of megabytes per player.

**`ReplayPolicy`'s limits are settings, not constants** (`YABRANKED_REPLAY_RETENTION_DAYS`, `_SAVED_PER_PLAYER`, `_SAVED_BYTES_PER_PLAYER`, `_MAX_RECORDING_BYTES`; sizes take a `k`/`m`/`g` suffix). The defaults — 7 days, 10 pinned, 2 GiB per player, 512 MiB per match — assume a host with room, and the host this runs on is a Pi with a nearly full SD card. Baking them in meant the only way to fit the disk was a rebuild.

**`YABRANKED_MATCH_LOG_DIR` keeps a match container's log past its container.** Teardown is `docker rm -f`, which destroys the only record of what happened *inside* a match — whether the agent configured YAB, whether the game ever ended, why a result never arrived. The backend copies the tail out to `<matchId>.log` **before** the remove (a log read afterwards is no log at all) and keeps the newest `logsKept`. Unset keeps the old behaviour of discarding them.

`YABRANKED_SEED=1` loads the fixture ladder from `dev/Seeder.kt` for UI work; it refuses to run against Postgres.

Client backend URL comes from `-Dyabranked.url`, then `$YABRANKED_URL`, defaulting to `YabRankedClient.DEFAULT_BACKEND_URL` — the **published** service, not localhost. A shipped jar is the case that must work with no configuration: a player installing the mod has no system property to set. Development is the case that can be asked to configure itself, so `runClient`/`runClient2` pass `-Dyabranked.url` explicitly (override the target with `-PyabrankedLocalBackend=…`). Without those the dev clients would quietly queue against production.

Replay packets go to S3-compatible storage when `YABRANKED_REPLAY_S3_BUCKET` and its access keys are set (`_ENDPOINT` for R2/MinIO, `_REGION` defaults to `auto`), else `YABRANKED_REPLAY_DIR`, else memory — which is now **capped** at `InMemoryReplayBlobStore.DEFAULT_MAX_TOTAL_BYTES`, because the failure mode of an unconfigured deploy was the heap, not the replays. S3 has no append, so each uploaded chunk is its own immutable object keyed by a zero-padded start offset; the padding is what makes S3's lexicographic listing and a byte-ordered walk the same thing.
